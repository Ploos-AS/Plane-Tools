# M5.9 — short-lived ADS-B cache and request coalescing

M5.9 reduces receiver load when several browser clients or API consumers refresh at nearly the same time.

## Behaviour

- Successful normalized ADS-B fetches are cached in memory for 1 second.
- The cache is shared by:
  - `GET /api/v1/adsb/status`
  - `GET /api/v1/adsb/aircraft`
  - `GET /api/v1/adsb/aircraft/search`
  - `GET /api/v1/adsb/snapshot`
- Concurrent cache misses are coalesced: one request performs the readsb/dump1090 fetch while the others wait for that result.
- Failed receiver requests are not cached, allowing immediate recovery on the next request.
- Changing receiver URL, timeout configuration or receiver coordinates invalidates cached data.
- The cache is process-local and ephemeral. It is never written to `/data`.

## Why one second

The web UI refreshes on a multi-second cadence, so a one-second cache is short enough to retain live spotting behaviour while absorbing refresh bursts and multiple clients that arrive together.

## Acceptance

- [x] Concurrent cache misses result in one upstream request.
- [x] Immediate repeated reads reuse the cached receiver result.
- [x] Expired cache entries trigger a new receiver fetch.
- [x] All ADS-B read endpoints share the same cache.
- [x] Receiver errors are not cached.
- [x] Configuration changes invalidate the cache.
- [x] No ADS-B history is persisted by the server.
