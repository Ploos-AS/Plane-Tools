# M5.15 — ADS-B receiver flapping detection

M5.15 adds local flapping detection on top of the bounded in-memory ADS-B event history from M5.14.

## Detection model

Plane Tools evaluates health-transition events from the most recent two-minute window.

A flap transition is counted only when the receiver crosses the healthy boundary:

- `healthy -> degraded/stale/offline`
- `degraded/stale/offline -> healthy`

Transitions between non-healthy states do not count as flapping.

The receiver is marked as flapping when at least four healthy-boundary transitions occur inside the two-minute window.

## Diagnostics API

`GET /api/v1/adsb/diagnostics` now includes:

- `stability`: `stable` or `flapping`
- `flapping`: boolean
- `flap_transitions`: number of qualifying transitions in the active window
- `flap_window_seconds`: detection window in seconds

The actual receiver `health` remains independent. For example, a receiver may currently be `healthy` while also being marked `flapping` because it has oscillated repeatedly during the last two minutes.

## Web UI

The ADS-B diagnostics panel shows a separate Stability metric. A flapping receiver is labelled `unstable / flapping` and visually highlighted.

The detail line also shows the number of qualifying flap transitions and the active window.

## Privacy and runtime properties

Flapping detection:

- uses only the existing in-memory health-transition history
- performs no ADS-B upstream request
- stores no receiver URL, credentials, coordinates, or aircraft data
- adds no persistence and no external telemetry dependency
- naturally clears after old transitions leave the two-minute window

## Qualification

Tests cover:

- detection at the four-transition threshold
- expiry of transitions outside the two-minute window
- exclusion of non-healthy-to-non-healthy transitions
- frontend hooks and absence of receiver-sensitive fields in the diagnostics JavaScript
