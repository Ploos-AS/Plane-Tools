# M5.14 — ADS-B error/recovery history

M5.14 adds a bounded, process-local event history for receiver health and fetch reliability.

## Events

Plane Tools records only structured, non-sensitive events:

- `error` when an upstream ADS-B fetch fails, with the stable error code.
- `recovery` on the first successful fetch after an error, carrying the previous error code.
- `health_transition` when receiver health changes between `healthy`, `degraded`, `stale`, and `offline`.

The history is capped at 64 events and is held only in memory. It is cleared on process restart.

## API

`GET /api/v1/adsb/history` returns events newest-first.

Events contain timestamp, event type, stable code/reason, and health transition fields where relevant. Raw receiver errors are not stored in history, so receiver URLs, credentials, coordinates, and aircraft payloads are not part of the history model.

## UI

The ADS-B diagnostics card now includes a Receiver history list. Diagnostics refresh reads only the local `/api/v1/adsb/diagnostics` and `/api/v1/adsb/history` endpoints; it does not trigger receiver polling.

## Qualification

M5.14 tests verify:

- the history remains bounded at 64 events;
- the API returns newest events first;
- recovery is emitted once after an error state;
- repeated identical health observations do not create duplicate transitions;
- the diagnostics UI uses the local history endpoint and contains no receiver URL/coordinate hooks.
