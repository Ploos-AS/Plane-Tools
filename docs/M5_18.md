# M5.18 — ADS-B outage classification

M5.18 classifies receiver outages from the bounded in-memory ADS-B health history introduced in M5.14 and used for availability in M5.17.

## Classification

Outages begin when health leaves `healthy` and end when health returns to `healthy`.

Classification is deterministic:

- under 15 seconds: `blip`
- 15–59 seconds with `upstream_status`: `upstream_status`
- 15–59 seconds with `timeout`: `timeout`
- 15–59 seconds with other receiver/feed reasons: `receiver_issue`
- 60 seconds or longer: `receiver_outage`

For an outage with multiple non-healthy transitions, `upstream_status` has priority over `timeout`; otherwise the most recent non-empty reason code is retained. Long duration always classifies as `receiver_outage` while preserving the underlying code.

An active outage is reclassified as its duration grows, so a short timeout can begin as `blip`, become `timeout`, and eventually become `receiver_outage` after 60 seconds.

## Diagnostics API

`GET /api/v1/adsb/diagnostics` can now include:

- `current_outage` for an active outage
- `last_outage` for the most recently completed outage

Each outage object contains only bounded local observability metadata:

- `active`
- `kind`
- `code`
- `duration_seconds`
- `started_at`
- `ended_at` for completed outages

No receiver URL, credentials, coordinates, raw error messages, or aircraft data are stored in or exposed through outage classification.

## UI

The ADS-B diagnostics panel shows the active outage class and duration as a first-class metric. The detail line also shows the current and last classified outage, including the stable reason code when available.

## Scope and retention

Outage classification is derived solely from the process-local 64-event ADS-B history. It performs no receiver fetches and adds no persistence. Results therefore reset when Plane Tools restarts and are limited by the retained history window.
