# M5.21 — ADS-B event-history cleanup

M5.21 makes the in-memory ADS-B event history more signal-oriented without changing its bounded, local-only design.

## Changes

- Repeated identical upstream fetch-error codes are de-duplicated until a successful fetch records recovery.
- The first occurrence keeps its original timestamp; later identical failures do not move the incident start time.
- After recovery, the same error code may be recorded again as a new incident.
- A changed error code is recorded as a new event so state changes remain visible.
- All bounded event insertion now goes through one locked append helper.
- The history remains capped at 64 events and is returned newest-first by the existing history endpoint.

## Semantics

Health-transition de-duplication is unchanged: only actual health-state changes create health-transition events.

Fetch recovery remains edge-triggered: one recovery event is written after one or more failed fetches, and repeated successful fetches do not create additional recovery events.

M5.21 does not add persistence, external telemetry, receiver polling, coordinates, credentials, raw error strings, or aircraft payloads to history.

## Why

Before M5.21, a receiver that remained unreachable could generate the same fetch-error event on every actual upstream fetch and eventually crowd useful health/outage transitions out of the 64-event buffer. M5.21 preserves the bounded-memory model while keeping the buffer focused on meaningful changes.
