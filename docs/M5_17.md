# M5.17 — ADS-B receiver availability window

M5.17 derives a small local availability estimate from the bounded ADS-B health-event history introduced in M5.14.

## Scope

- No new ADS-B receiver polling.
- No persistence.
- No external metrics or telemetry service.
- No receiver URL, credentials, coordinates or aircraft data in availability state.
- Calculations use only retained `health_transition` events.

## Availability semantics

`healthy` counts as available. `degraded`, `stale` and `offline` count as unavailable.

The observed window starts at the oldest retained health transition and ends at the current evaluation time. Because the event history is bounded to 64 events and is process-local, this is a **history-window estimate**, not a lifetime SLA or persistent uptime record.

Diagnostics now expose:

- `availability_known`
- `available_now`
- `availability_percent`
- `availability_window_seconds`
- `current_uptime_seconds`
- `last_outage_seconds`

`current_uptime_seconds` is set only while the current health state is `healthy`. `last_outage_seconds` reports the most recent completed non-healthy interval; an outage that is still active is not reported as a completed outage.

## UI

The ADS-B diagnostics card shows:

- Availability percentage for the retained history window.
- Current uptime while available.
- Length of the observed availability window.
- Duration of the last completed outage, when one exists.

The diagnostics UI still reads only Plane Tools local API endpoints.

## Qualification

Tests cover:

- A fully healthy observation window (100% availability).
- A completed outage and recovery with deterministic availability percentage.
- An active outage.
- Unknown availability with no retained health history.
- Frontend field hooks and the prohibition on direct receiver access from diagnostics JavaScript.
