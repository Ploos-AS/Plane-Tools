# M5.16 — ADS-B recovery stabilization / hysteresis

M5.16 prevents receiver stability from returning to `stable` immediately after a flapping episode.

## Behavior

Flapping detection still uses the M5.15 rule:

- 2 minute detection window
- 4 healthy-boundary transitions
- only transitions between `healthy` and a non-healthy state count

Once flapping has been detected, the state is latched. The latch clears only after a continuous 2 minute quiet period since the most recent healthy-boundary transition.

A new healthy-boundary transition during recovery restarts the quiet-period timer.

The current receiver health remains independent from stability. A receiver may therefore be `healthy` while stability remains `flapping` during the recovery period.

## Diagnostics

`GET /api/v1/adsb/diagnostics` exposes:

- `stability`
- `flapping`
- `stabilizing`
- `flap_transitions`
- `flap_window_seconds`
- `flap_recovery_quiet_seconds`
- `flap_recovery_remaining_seconds`

The diagnostics UI displays `unstable / stabilizing` and the remaining quiet-period seconds while the latch is recovering.

## Scope and privacy

Recovery state is process-local and in-memory only. It does not trigger ADS-B receiver requests and does not persist receiver URLs, credentials, coordinates, raw errors, or aircraft data.

## Qualification

Automated tests cover:

- latching after the flapping threshold is reached
- remaining unstable while the raw 2 minute threshold has already fallen below four transitions
- resetting the recovery timer after a new healthy-boundary transition
- clearing the latch only after the full 120 second quiet period
- frontend stabilization hooks remaining local-only
