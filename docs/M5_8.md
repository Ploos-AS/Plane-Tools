# M5.8 — ADS-B receiver polling efficiency

M5.8 removes the browser's duplicate receiver polling path.

## Snapshot API

`GET /api/v1/adsb/snapshot`

The endpoint performs one read of the configured readsb/dump1090 `aircraft.json` feed and returns:

- `status`: receiver configuration/reachability, aircraft count, message count and receiver-position state
- `aircraft`: the filtered and sorted aircraft list

The snapshot accepts the same query parameters as `/api/v1/adsb/aircraft/search`:

- `q`
- `min_altitude_ft`
- `max_altitude_ft`
- `max_distance_nm`
- `sort`
- `order`

`status.aircraft` is the total upstream aircraft count before UI filters; `aircraft` contains the filtered result.

## Browser polling

The live ADS-B UI now calls only `/api/v1/adsb/snapshot` for each refresh. Previously it called `/api/v1/adsb/status` and then `/api/v1/adsb/aircraft/search`, causing two upstream reads of `aircraft.json` every refresh interval.

The refresh timer is re-armed after the M5.2 ADS-B override is installed so automatic refreshes also use the snapshot path.

## Compatibility

The existing endpoints remain available:

- `/api/v1/adsb/status`
- `/api/v1/adsb/aircraft`
- `/api/v1/adsb/aircraft/search`

They are retained for API compatibility. The embedded web UI uses the snapshot endpoint.

## Qualification

Tests verify that a snapshot request performs exactly one upstream receiver request while preserving filtering, status counts and disabled-receiver behavior.
