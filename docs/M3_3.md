# M3.3 — Spotting location CRUD and airport binding

Status: implemented

## Goal

Make saved spotting locations maintainable and allow a spot to be associated with a specific airport instead of always relying on nearest-airport inference.

## API

- `GET /api/v1/spotting-locations`
- `POST /api/v1/spotting-locations`
- `PUT /api/v1/spotting-locations/{id}`
- `DELETE /api/v1/spotting-locations/{id}`
- `GET /api/v1/spotting-locations/analyze?id={id}`

`airport_ident` is optional when creating or updating a location. When present it must match an airport `ident` in the local airport database.

Example:

```json
{
  "name": "Kjevik west",
  "latitude_deg": 58.21,
  "longitude_deg": 8.07,
  "airport_ident": "ENCN"
}
```

Saved locations receive a stable slug-style `id`. Existing M3.2 JSON entries without an ID are assigned deterministic IDs when loaded.

## Analysis semantics

When a saved location has `airport_ident`, analysis uses that airport and returns `bound: true`. Without a binding, the nearest local airport is selected and `bound` is false.

Ad-hoc coordinate analysis can also provide `airport_ident` as a query parameter.

## Persistence

The existing `/data/spotting-locations.json` storage remains in use. Create, update and delete operations use the same atomic replacement strategy introduced in M3.2.

## Acceptance criteria

- [x] Saved locations have stable IDs.
- [x] Locations can be updated.
- [x] Locations can be deleted.
- [x] Optional airport bindings are normalized and validated locally.
- [x] Analysis honours an explicit airport binding.
- [x] Existing ID-less M3.2 entries remain loadable.
- [x] No external API is required.
